# Implementation Plan: Core Engine

**Branch**: `001-core-engine` | **Date**: 2026-09-06 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/001-core-engine/spec.md`

## Summary

Build an agnostic data processing engine that receives raw content (text, HTML, PDF, JSON), processes it through configurable LLM-powered pipelines (Ingest → Dedup → Process → Validate → Persist), and outputs structured results to project-specific sinks. The engine is designed as a standalone, reusable service — each project (VotoLimpo, Help Core, etc.) registers a pipeline via YAML config without touching engine code. Full cost metrification per call, per execution, per project with budget enforcement.

## Technical Context

**Language/Version**: Python 3.12
**Primary Dependencies**: FastAPI, asyncpg, httpx, openai, pydantic, pydantic-settings, PyMuPDF, beautifulsoup4, jsonschema, PyYAML, alembic, SQLAlchemy (models only)
**Storage**: PostgreSQL 16 with pgvector extension (schema: `processing_engine`)
**Testing**: pytest + pytest-asyncio + testcontainers (real PostgreSQL, zero DB mocks)
**Target Platform**: Linux server (Docker container, python:3.12-slim)
**Project Type**: Single (API + Worker in same container)
**Performance Goals**: <30s per item (5k words), batch of 100 in <10min, dedup <100ms, cache hit <200ms
**Constraints**: <200MB Docker image, <$10/month for 10K items with gpt-4.1-mini, single PostgreSQL dependency
**Scale/Scope**: 500-1000 items/day per project, multiple projects sharing one engine instance

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| # | Principle | Status | Evidence |
|---|-----------|--------|----------|
| I | Agnóstico por Design | PASS | Pipeline config via YAML/API, zero project-specific code in engine. Plugins for all stages. |
| II | Anti-Reprocessamento (NON-NEGOTIABLE) | PASS | 3 layers: url_hash (FR-004), content_hash (FR-004), result cache (FR-010). Dedup BEFORE LLM call. |
| III | Custo Controlado e Metrificado | PASS | llm_call_log table (FR-019), model_pricing (FR-020), /v1/costs endpoint (FR-021), budget limits (FR-022), ALL calls tracked including retries (FR-023). |
| IV | Plugin-First | PASS | typing.Protocol for all 5 stages. Zero inheritance, structural subtyping. |
| V | Stack Mínima | PASS | Only PostgreSQL (+ pgvector). Job queue via SKIP LOCKED. No Redis, no RabbitMQ. |
| VI | Schema First | PASS | Alembic migrations, JSON Schema validation, OpenAPI 3.1 contracts. |
| VII | Idempotência Total | PASS | idempotency_key (FR-015), upsert sinks (ON CONFLICT), deterministic LLM (temperature=0, seed). |
| VIII | Observabilidade | PASS | processing_logs per step (FR-008), llm_call_log per call (FR-019), /v1/stats and /v1/costs endpoints. |
| IX | Testabilidade | PASS | testcontainers with real PostgreSQL. Protocol mocks for LLM in unit tests. Zero DB mocks. |
| X | Segurança | PASS | X-API-Key header on all endpoints except /health. Parameterized queries via asyncpg. No arbitrary code execution. |

**Result: 10/10 PASS — all gates clear.**

## Implementation Phases

### Phase A: Foundation (database + config + health)

**Goal**: PostgreSQL schema running, basic config, health endpoint.

**Files**: `app/config.py`, `app/db.py`, `app/main.py`, `app/api/health.py`, `alembic/`, `db_models/`, `docker-compose.yml`, `pyproject.toml`, `.env.example`, `Dockerfile`

**Deliverables**:
1. `pyproject.toml` with all dependencies
2. `app/config.py` — Settings class with all env vars
3. `app/db.py` — asyncpg pool lifecycle
4. `app/main.py` — FastAPI app with lifespan
5. `app/api/health.py` — GET /health (no auth)
6. `docker-compose.yml` — postgres:16 with pgvector
7. Alembic setup + migrations 001-010 (all tables)
8. `db_models/` — SQLAlchemy models for migration autogenerate
9. `Dockerfile` — multi-stage, python:3.12-slim
10. `tests/conftest.py` — testcontainers fixture

**Tests**: health endpoint returns 200, DB connection works, migrations apply cleanly.

### Phase B: Plugin System (protocols + registry + built-in plugins)

**Goal**: All 5 plugin protocols defined, registry works, built-in implementations.

**Files**: `app/plugins/protocols.py`, `app/plugins/registry.py`, `app/plugins/ingestors/*`, `app/plugins/dedup/*`, `app/plugins/llm/*`, `app/plugins/validators/*`, `app/plugins/sinks/*`

**Deliverables**:
1. `protocols.py` — 5 Protocol classes (Ingestor, DedupStrategy, LLMProvider, Validator, Sink)
2. `registry.py` — Plugin registry with register/get/list
3. Ingestors: html, pdf, text, json, auto
4. Dedup: hash, semantic (pgvector), composite
5. LLM: openai (completions + embeddings)
6. Validators: schema, grounding, range, date
7. Sinks: postgresql (upsert)

**Tests**: Unit tests for each plugin. Mock LLM responses in unit tests.

### Phase C: Cost Tracker Service

**Goal**: LLM call logging, cost calculation, budget enforcement.

**Files**: `app/services/cost_tracker.py`, `app/api/costs.py`, `app/api/pricing.py`, `app/models/cost.py`, `app/sql/costs.sql`

**Deliverables**:
1. `cost_tracker.py` — CostTracker class: log_call(), calculate_cost(), check_budget()
2. `app/api/costs.py` — GET /v1/costs with all filters and group_by
3. `app/api/pricing.py` — GET/POST /v1/pricing
4. `app/models/cost.py` — Pydantic models for cost report
5. `app/sql/costs.sql` — Aggregation queries

**Tests**: Unit tests for cost calculation. Integration tests for budget enforcement (80% warning, 100% block).

### Phase D: Pipeline Management (CRUD + versioning)

**Goal**: Register, update, list pipelines. Version snapshots.

**Files**: `app/api/pipelines.py`, `app/models/pipeline.py`, `app/cli.py`

**Deliverables**:
1. `app/api/pipelines.py` — POST/GET/PUT /v1/pipelines
2. `app/models/pipeline.py` — PipelineCreate, Pipeline response models
3. `app/cli.py` — `register-pipeline` command (YAML → DB)
4. Version increment on update (FR-016)

**Tests**: Create pipeline, update pipeline (version bumps), list pipelines, validation errors.

### Phase E: Orchestrator (pipeline execution engine)

**Goal**: Core processing pipeline: ingest → dedup → process → validate → persist.

**Files**: `app/services/orchestrator.py`, `app/deps.py`

**Deliverables**:
1. `orchestrator.py` — Orchestrator class with process_item() method
2. Step-by-step execution with processing_log per step
3. Retry logic with exponential backoff (FR-018)
4. Cache check/save (FR-010)
5. Cost tracking integration (FR-019, FR-023)
6. Content truncation (FR-017)

**Tests**: Integration test with real PostgreSQL: submit item, verify all steps logged, output valid, cost tracked.

### Phase F: Job API + Worker

**Goal**: Submit jobs, worker claims and processes, real-time counters.

**Files**: `app/api/jobs.py`, `app/worker.py`, `app/models/job.py`, `app/models/item.py`, `app/services/callback.py`, `app/sql/jobs.sql`, `app/sql/items.sql`

**Deliverables**:
1. `app/api/jobs.py` — POST /v1/jobs, GET /v1/jobs/{id}, GET /v1/jobs/{id}/result, GET /v1/jobs/{id}/logs
2. `app/worker.py` — SKIP LOCKED polling loop with asyncio.Semaphore for concurrency
3. Idempotency key check (FR-015)
4. Budget check before processing (FR-022)
5. Callback on completion (FR-013)
6. Real-time counter updates (items_completed, items_failed)

**Tests**: Full integration: submit job, worker processes, check results. Batch test with concurrency. Duplicate idempotency_key returns 409. Budget exceeded returns 429.

### Phase G: Stats + Auth

**Goal**: Aggregated metrics endpoint, API key authentication.

**Files**: `app/api/stats.py`, `app/models/stats.py`, `app/sql/stats.sql`, `app/deps.py`

**Deliverables**:

2. `app/deps.py` — verify_api_key() dependency
3. Auth middleware on all /v1/* endpoints

**Tests**: Stats accuracy after processing jobs. Unauthorized request returns 401.

**Deliverables**:

3. `.github/workflows/ci.yml` — lint + test + build
4. `tests/contract/test_openapi.py` — validate API matches OpenAPI spec
